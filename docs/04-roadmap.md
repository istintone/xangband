# 4. 開発ロードマップ

各マイルストーンは**「その時点で何が遊べるか」**と**受け入れ基準**で定義する。
基準を満たすまで次に進まない。工数は目安(1人・Claude Code 併走前提)。

- [x] Canvas 疑似ターミナル(80x40 グリッド、等幅グリフ、16色パレット、差分描画)
- [x] 単純な部屋+通路生成(ブロック配置・内室・L字通路・扉・**連結性検証と再試行**)
- [x] 移動・壁判定・再帰シャドウキャスティング視界・既知グリッド記憶・常時照明区画
- [x] メッセージ行 + サイドバー(HP/深度/ターン/位置/光/シード)
- [x] マップ(論理120x50)と端末(80x40)の分離 + 追従ビューポート (`[[D-21]]`)
- [x] グリフ中間表現 `{ch,fg,bg,w}` (`[[D-22]]`)。**全角2セル対応**
- [x] ヘッドレス検証ハーネス `src/tests/run.js` (決定論/不変条件/統計の三層)

**受け入れ基準**: 同じシードで**必ず同じダンジョン**が生成される(テストで検証)。
→ **達成**。`node src/tests/run.js` が 17 pass / 0 fail。
120階層で連結性・外周・階段の不変条件を検証し、生成の再試行は平均 1.00 回。

### M0 で分かったこと
- 固定幅グリッドに日本語を出す以上、**全角2セル対応は最初から要る**。
  後回しにするとメッセージ行を出した瞬間に全ての桁がズレる。`isWide()` で判定し、
  グリフバッファに `w = 1|2|0`(半角/全角先頭/全角後続)を持たせて解決した。
- 生成器は「試行ごとに独立したRNGを derive する」ことで、失敗した試行が
  後続の乱数をズラさないようにした。これをしないと再試行が起きた階だけ再現性が壊れる。

- [x] 階段による昇降。深度スケーリング(alloc table + OOD)
- [x] 経験値・レベルアップ・HP成長
- [x] 死亡 → 墓碑 → スコア記録(パーマデス)
- [x] `localStorage` セーブ/ロード(乱数状態を含む = セーブスカム不可)
- [x] `src/data/*.json` をコンテンツの正本にし、`build.py` が埋め込む (`[[D-25]]`)
- [x] 所持品・装備・墓碑・ヘルプの画面(`ui.js`)

**受け入れ基準**: 深度10 まで潜れて、そこで死ねる。**1000回のランダム自動プレイでクラッシュ 0**。
→ **達成**。`node src/tests/autoplay.js --runs 1000` が **クラッシュ 0**
(到達深度 平均5.1 / 最大15、レベル 平均3.2 / 最大9)。
`node src/tests/run.js` は 31 pass / 0 fail。

### M1 で分かったこと
- **自動プレイが最大の検証装置だった。** 手で数十ターン触っても出ない不具合が2件出た。
  1. **エネルギーの二重消費** — `Cmd.step` と `Turn.tick` の両方がプレイヤーのエネルギーを引き、
     ターンが永久に進まなかった。`Turn.tick` の戻り値を `STOP/SKIP/ACTED` に明示し、
     **エネルギーを引くのは tick だけ**という契約にして解消。
  2. **死者の蘇生によるゾンビ状態** — 死亡直後に自然回復が働き、`dead` フラグが立ったまま
     HP が戻る。スケジューラは死者を飛ばすのでターンが永久に進まない。
     **死を一方通行**にし(`Actor.heal` は死者に効かない)、死亡判定は `dead` フラグも見るようにした。
- **モンキーテストは「賢さ」を足さないと何も検査しない。** 完全ランダムだと壁に張り付いて
  戦闘にも降下にも到達しなかった。テスト側に BFS 経路探索と交戦バイアスを入れて初めて、
  深部のコードが叩かれるようになった。
- **レベル1の HP 10 は低すぎた。** 本家は「系統 + ロール」のヒットダイス合算(人間10+戦士9=19)。
  合わせたところ、到達深度の平均が 2.7 → 5.1 に改善した。

**受け入れ基準**: **深度40 相当まで通しでプレイできる**。
本家経験者が触って「Angband の骨格だ」と分かる。ここが**ベースライン完成点**。
→ **達成**。`node src/tests/run.js` の「★深度40 まで通しで潜れる」が通り、
各階で敵・アイテム・連結性・階の予感がすべて成立している。
テストは 57 pass / 0 fail、自動プレイは**全64通りの系統×ロールでクラッシュ0**。

### M2 で分かったこと
- **経路探索を入れたら、睡眠が必須になった。** 音のマップ(`[[D-35]]`)を実装した途端、
  全ての敵が初手からプレイヤーへ殺到し、到達深度が 5.1 → 2.6 に落ちた。
  本家に敵の睡眠があるのは難易度調整ではなく、**探索という行為を成立させるため**だった。
  睡眠を入れて初めて隠密技能にも意味が生まれた (`[[D-40]]`)。
- **能力値を完全ランダムにすると、ロールの個性が乱数で消える。** 4d4+2 で振ったところ
  主能力値の平均が 12 まで落ち、「主能力値 8 の念導者」のような成立しないランが出た。
  本家のポイント割り振りも「主能力値は必ず良い」ことを保証している (`[[D-41]]`)。
- **速度の価値を守る設計は、序盤にそれを出さないことと表裏一体。** 深度3 に速度+10 の敵を
  置いていたが、行動回数2倍を序盤の HP で受けきる方法が無かった (`[[D-42]]`)。
- **データ検証を生成時に走らせるのが効いた。** `Data.validate()` が
  「存在しないアイテム種別を参照する固有機材」「機械系ロールに割り当てた精神系能力」を
  実行前に落とした。どちらも実プレイでは滅多に踏まない経路にあった。

## M2.5 — 設計フェーズ (2026-09-09)
**目標: M3 に入る前に、サイトを飾りにしないための設計を確定させる。**

M2 でベースラインが完成した時点で、**「4サイトあるのに1サイトだけ潜れば勝てる」**
という設計上の穴が見えた。実装に入る前に4本の設計文書を書いた。

- [x] [最終ゴール設計](07-endgame.md) — 《適合》4種で4サイトを勝利条件に接続 (`[[D-44]]`)
- [x] [惑星環境の設計](08-environment.md) — 7つの環境値・気密・減圧の伝播・昼夜 (`[[D-46]]`)
- [x] [UIの設計](09-ui.md) — M2 で判明した不足 U-1〜U-9 の解消 (`[[D-48]]`〜`[[D-52]]`)
- [x] [細部デザインの差別化設計](10-differentiation.md) — 判定基準と測れる指標 (`[[D-53]]`)

### 設計で分かったこと
- **勝利条件に4サイトを組み込まないと、サイトは飾りになる。** 鍵集めのお使いにせず、
  既にある環境という軸を勝利条件に接続した(`[[D-44]]`)。新機構を足していない。
- **`seal` と `exposure` は M2 時点で「値はあるが誰も要求しない」状態だった。**
  環境を実装するとは、値を増やすことではなく**それを要求する場所を作る**こと。
- **M2 の最大の穴は注視/目標指定の欠如だった。** 遠隔と能力を実装したのに
  「どれを狙うか」がプレイヤーの手に無かった(`[[D-49]]`)。

### M3a で分かったこと
- **測定単位を間違えると較正を誤る。** 環境ダメージを `Cmd.step` 1回=1ターンで
  測っていたが、実際は速度110で**約10ゲームターン**進む。10倍の値を見て
  「環境が過激すぎる」と判断しかけた。ゲームターン基準で測り直して解決。
- **自然回復を含めずに環境を測っても意味がない。** 単独で `Env.tick` を回すと
  致死的に見えるが、実ループでは回復が上回る。**実ループで測る**のが正しい。
- **派生値は直接代入で試験できない。** `p.seal` は毎ターン装備から再計算されるので、
  テストで直接代入しても `recalc` が上書きする。テストは実装備で作る必要があった。
  これはテストの欠陥だったが、実装の性質(seal は派生値)を確認する機会にもなった。
- **キーを知らない人が遊べないゲームになっていた。** `x` `f` `m` を知らなければ
  画面を見ても手が出ない。端末の**外**に DOM でパネルを置き、
  すべてのコマンドをボタンにして、状況に応じたヒントを出すことで解決した(`[[D-55]]`)。
  端末 80x40 の中に入れなかったのは、既にサイドバー16桁を使っており
  これ以上マップを削れないため。DOM ならクリック・文字選択・折りたたみも無料で付く。

## M3b — 4サイトと星系 (目安 2〜3週)
**目標: 本作固有の構造が立ち上がる。ここから「クローン」ではなくなる。**

- [x] `sites.json` — 5サイトの環境プロファイル・生成パラメータ・敵/アイテムの重み
- [x] サイト別生成器(まずパラメータで到達できる差を使い切る — `[[doc:differentiation]]` §10.5)
- [x] 星系マップ(降下先の選択)。サイトごとの到達最深度
- [x] 減圧の伝播(方舟) / 昼夜(灰) / 監視と増援(尖塔) / 完全暗黒(遺跡)
- [x] サイト固有の敵プール(固有報酬・固有ユニークは M4)
- [x] 《適合》4種(取得のみ。深度80以降の複合環境は M4)

**受け入れ基準**: 4サイトそれぞれが**明確に違う遊び**になっている。
判定は `[[D-53]]` の指標で行う:
**サイトごとに最頻死因が違う / 環境ダメージが総被ダメの15〜35% /
撤退理由の半分以上が HP 以外 / どのサイトも到達深度が極端に低くない**。

### 判定結果 (`node src/tests/autoplay.js --metrics --runs 60`)

| 指標 | 結果 |
|---|---|
| サイトごとに最頻死因が違う | **達成**(方舟=減圧 / 灰=掃引機 / 遺跡=虚空追い / 尖塔=企業保安) |
| 撤退理由の半分以上が HP 以外 | 遺跡80% / 尖塔100% は達成。方舟42% / 灰33% は未達 |
| 環境ダメージが総被ダメの15〜35% | **指標そのものを見直す必要がある** → `[[Q-19]]` |
| どのサイトも到達深度が極端に低くない | **測定器の限界で判定できない** → `[[Q-20]]` |

実測値と、達成できていない2つの理由は
[[doc:differentiation]] §10.8 に記録した。要点は:

- 「全サイトで環境ダメージ15〜35%」は、`docs/08` §8.7 の
  「**尖塔だけ環境が安全**」という設計と矛盾する。
  指標が4サイトの設計より先に書かれていた。
- 自動プレイヤーは店で最初に買える物を買うだけで性能を比較しないので、
  深度10/20 から始まる遺跡・尖塔に**装備が足りないまま**入って死ぬ。
  サイトの難易度ではなく測定器を見ている。

### この段階で分かったこと
- **サイトを実装した瞬間、新規ランが成立しなくなった。** 既定の降下先が方舟になり、
  深度1の通路が真空で初期装備(気密1)では一歩も動けない。
  「最初の5分は完全に Angband であるべき」の最低条件は呼吸できることだった (`[[D-61]]`)。
- **破断を一律の真空にすると、装備の階段と噛み合わない。** 深度1でも深度40でも
  必要気密4 になり、装甲スーツが買える深度10 未満では**入る手段が存在しない**区画が
  生まれていた。破断の**深さ**も深度で変えた (`[[D-62]]`)。
- **数字が動くことと、数字が意味を持つことは別。** 同じ修正の前後で環境ダメ比が
  80% → 48% → 77% と揺れた。自動プレイヤーの経路取りが支配的で、
  この指標では方舟の調整の可否を判定できない。**再現するのは最頻死因と撤退理由だけ**。
- **輪郭を崩す生成は、連結性検証を25%落としていた。** 削った縁の外に小さな床の袋が残る。
  捨てずに埋めれば不変条件は保たれる (`[[D-63]]`)。
- **測る道具を作ると、測りたかったもの以外が先に見つかる。** 上の3件はすべて
  `--metrics` を書いた副産物で、テストでは1件も落ちていなかった。

## M4 — 終端まで通す (目安 2〜3週)
**目標: 終わりまで到達できる。**

**終端から作る** ([[D-64]])。受け入れ基準が「通しクリアが可能」の一点である以上、
深部ユニーク→《起源》→《門番》→撃破→帰還→勝利画面 が繋がるまで基準は0%のまま動かない。
電脳層と加工/解体は、その形が立ってから足す。

### M4a — 勝利までの一本道 ✅

- [x] 敵の遠隔攻撃 ([[D-68]])。《門番》の前提として先に入れた
- [x] 守護ユニーク4体と《適合》の取得動線。最深階に確定配置 ([[D-69]])
- [x] ログ断片 `lore.json` 29片。拾って読む・所持品に入らない・収集数を数える ([[D-67]])
- [x] 《起源》深度80〜100 の構造(接続層80-89 / 中枢層90-97 / 静止層98)
- [x] 《門番》(深度99)。4つの環境ハザードを攻撃として撃つ = 《適合》の最終確認
- [x] 《起源》(深度100)
- [x] 帰還フェーズ。撃破後に母船まで戻って初めて勝利 ([[D-70]] [[D-71]])
- [x] 勝利画面とスコア記録。収集した断片の数で結末の解像度が変わる
- [x] 開発用の起動オプション ([[D-66]])

**通しの確認**: 深度99 で《門番》を撃破 → 降下シャフト開通 → 深度100 で
《起源》を撃破 → 帰還フェーズ → 10ホップで母船 → 勝利画面と記録、
までを実際に歩いて確認した。ブラウザでも `?dev=` で同じ画面を撮っている。

**この段階で分かったこと**:
- **《起源》(深度100)の中央のボス区画が壁で完全に塞がっていた。** 最終戦に
  到達できない。生成器には連結性検証があるのに固定マップには無かった (`[[D-72]]`)。
- **階段の無い側から入ると落ちた。** 《門番》の降下シャフトは倒すまで開かないので、
  深度100 から上がって再訪すると `lv.down` が無い。実際にプレイヤーが通る経路だった。
- **崩壊の圧を減圧でかけても何も起きない。** 深度80以降に来たプレイヤーは
  《適合》を4つ持っているので、環境4種はどれも効かない (`[[D-71]]`)。
- **深度100 の階が「危険2」と出ていた。** 予感は敵の数を積む式なので、
  単体の格上を過小評価する (`[[D-73]]`)。
- **通しで歩いて初めて出た不具合ばかり。** 上の4件はテストでは1件も落ちていない。

### この段階で分かったこと
- **専門家の成功率が上限に張り付いていた。** 接続技能はレベルで伸びるので、
  ICE 難度が深度/3 だと伸びに追い越される。レベル25 の接続者が全操作95%だった。
  **深部では専門家でも確実でない**ことが、認知の使いどころの判断を作る (`[[D-74]]`)。
- **端末の出現率はサイトで20倍近く違う**(尖塔90% / 遺跡5%)。
  端末を待つだけのロールにすると、遺跡では接続者が20階ぶん何もできない。
  **ロールの機能が地形の運に依存してはいけない** (`[[D-75]]`)。
- **枠外UI のテストが手書きの一覧を持っていて、ボタンを足したら落ちた。**
  受け口の一覧をソースから読むように変えた ―― 手で並べた表は必ずズレる。

**受け入れ基準**: **通しクリアが可能**。
開発用の起動オプションで深度80/98/99/100 と帰還を実際に通し、
自動プレイでも深度100 到達を試みる ([[D-66]])。
通しプレイでの確認は M5 で行う。

> **未達の前提**: 敵は深度28まで、アイテムは深度20までしか存在しない。
> 深度29〜100 は既存の浅い敵で埋まるので、**構造としては通せてもバランスは測れない**。
> いつ埋めるかは `[[Q-21]]`。

### この段階で分かったこと
- **深度90 の階に深度1 の敵とバールが同じ確率で出ていた** (`[[D-77]]`)。
  コンテンツを足して初めて見えた ―― 中身が無いうちは、抽選の欠陥も見えない。
- **サイトの重みが 1 より大きい指定を無視していた** (`[[D-76]]`)。
  データの書き手の意図を半分しか読んでいなかった。
- **自分で書いた色覚配慮パレットが、赤と緑の輝度差 8 だった** (`[[D-79]]`)。
  自分のテストに落とされた。色相を置き換えるだけでは配慮にならない。
- **一覧の色が、文字より多くを漏らしていた** (`[[D-78]]`)。
  未解析の改修品が青く、刻印式鑑定が骨抜きになっていた。
- **接続者は核の機構に触れないまま死ぬのが標準だった** (`[[D-80]]`)。
  強さではなく「設計したものが遊ばれるか」の問題。
- **封鎖区画が密なサイトで実測 0〜1/60 だった** (`[[D-81]]`)。
  データは在ったが、置く順序のせいで**機能が存在しないのと同じ**だった。
  「在るか」と「出るか」は別の問いで、後者は測らないと分からない。
- **「通しクリアは成立しない」という自分の結論が、測定器の欠陥だった** (`[[D-89]]`)。
  店売り装備だけ・能力値は初期値のままのボットで測って全関門 0% を見て、
  設計が破綻していると報告した。現実的な装備で測り直すと全て越えられた。
  **数字を読む前に、数字を出した道具を疑う。**
- **召喚が連鎖して、20手で盤面が2体から43体に膨れていた** (`[[D-90]]`)。
  召喚する敵が22%あり、うち3体は呪文が召喚しかない ―― 召喚した相手がまた召喚する。
  そのせいで**深度60の関門が深度100より難しい**という順序の逆転が起きていた。
- **終盤の関門が中盤より易しい** (`[[Q-22]]`)。
  `s-slay-aberrant` だけ倍率が4で、深い武器の改修品3種がこれを積み、
  深部の敵は `aberrant` が最多。**深さではなく「スレイが噛み合うか」で難度が決まっていた**。

## 検証戦略(全マイルストーン共通)

ルール層が DOM 非依存(§docs/01.5-3)なので、Node から直接叩ける。

| 層 | 内容 |
|---|---|
| **決定論テスト** | シード固定で生成・戦闘・成長が完全再現されること。回帰の一次防衛線 |
| **不変条件テスト** | 全階段が到達可能 / アイテムが壁に埋まらない / エネルギーが発散しない / 所持品の重複IDが無い |
| **自動プレイ(モンキー)** | ランダム入力で N ラン走らせクラッシュと例外を検出。M1 以降 CI 代わりに常用。**強さの判定には使わない** ([[D-89]]) |
| **関門テスト** | 到達しうる強さを直接与えて、各関門を実ルールで戦わせる。**腕前と設計を切り分ける**唯一の層 ([[D-89]]) |
| **統計テスト** | 1000ラン分の「平均到達深度・死因分布・アイテム出現率」を出力。バランス調整の根拠にする |

### コミット前に通すもの
```sh
node src/tests/run.js               # 決定論 / 不変条件 / 統計 / 機構
node src/tests/panel.js             # 枠外UI(DOM スタブで組み立てとクリックを検査)
node tools/shot.js                  # 画面を撮って目で確認する ([[D-58]])
node tools/check_render.js          # 描画をピクセル単位で検査 ([[D-59]])
node src/tests/autoplay.js          # 自動プレイ(既定200ラン)。受け入れ判定は --runs 1000
node src/tests/gatecheck.js         # 関門を越えられるか ([[D-89]])。--gear poor/plain/rich
node tools/gen_reference.js         # 参照表の再生成 (データを変えたら必ず)
node tools/check_code.js            # コードの不変条件 K-1〜K-4 (docs/01 §1.5)
node tools/check_docs.js            # 企画書の整合性 C-1〜C-10 (docs/06 §6.9)
python build.py --check             # index.html / data-gen.js と src/ の乖離
```

`--by-combo` を付けると系統×ロール別の到達深度が出る(弱すぎる組み合わせの検出)。

> `--runs 1000` は約100秒かかる。日常は既定の200ランで回し、
> マイルストーン完了時とリリース前に1000ランを通す。
