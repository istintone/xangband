# 6. 文書運用ルール

> **このルールだけは `status: fixed`。** 他の文書は変わってよいが、
> 「どう変えるか」の手順は変えない。ここが崩れると企画書が実装から乖離する。

---

## 6.1 三層の正本(Source of Truth)

| 層 | 正本 | 誰が書くか | 例 |
|---|---|---|---|
| **設計意図** | `docs/*.md` | **手書き** | なぜ深度を共通化したか、気密の狙い |
| **コンテンツ数値** | `src/data/*.json` | **手書き** | 敵のHP・出現深度、アイテムの効果値 |
| **参照表 / スポイラー / wiki** | `docs/reference/**`, `dist/**` | **生成物・手書き厳禁** | 敵一覧表、固有機材一覧 |

### ★最重要ルール
> **数値の一覧表を `docs/*.md` に手書きしてはならない。**
> 一覧はすべて `src/data/*.json` から生成し、docs からはリンクで参照する。

理由: 手書き転記は必ず腐る。card-eleven で確立済みの方式をそのまま踏襲する。
docs に書いてよい数値は「**設計上の意図を持った代表値**」だけ
(例:「速度+10 = 行動2倍」)。個体データの羅列は書かない。

---

## 6.2 変更の手順(必ずこの順)

```
① docs/*.md を更新   ← 先に意図を書く
② 実装 / src/data を変更
③ 生成物を再生成      node tools/gen_reference.js
④ 検査を通す          node tools/check_docs.js && python build.py --check
⑤ CHANGELOG.md に追記
```

- **①を飛ばさない。** 「実装してから後で書く」を許すと必ず書かれない。
- ②で仕様が変わったら①に戻る。docs と実装が食い違ったら **docs を正**として実装を直す
  (docs 側が間違っていたと判断した場合のみ、理由を D-nn に残して docs を直す)。

---

## 6.3 更新トリガー(いつ書くか)

「気づいたら書く」は機能しない。**以下が起きたら必ず書く**、と引き金を固定する。

| 起きたこと | 書く場所 |
|---|---|
| 仕様を決めた / 変えた | 該当 `docs/*.md` + `CHANGELOG.md` |
| 「なぜそうしたか」の判断をした | `docs/05` の **決定事項 D-nn** に追記 |
| 判断を保留した / 悩んで先送りした | `docs/05` の **未決事項 Q-nn** に追記 |
| 保留していた Q-nn を決めた | Q-nn を `resolved` にし、**D-nn として昇格**して記録 |
| 新しい用語・固有名詞を作った | `src/data/glossary.json` |
| コンテンツ(敵/アイテム/系統)を追加した | `src/data/*.json` のみ。**docs は触らない** |
| マイルストーンの項目を完了した | `docs/04` のチェックボックス |
| マイルストーンを完了した | `docs/04` の受け入れ基準を確認 + 各 doc の `status` 見直し |
| バランス値を調整した | `src/data/*.json` + 根拠を `CHANGELOG.md` に一行 |

---

## 6.4 フロントマターと status

すべての `docs/*.md` は先頭に YAML フロントマターを持つ。**wiki 化の際のページ識別子になる。**

```yaml
---
doc: concept          # 安定ID。一度決めたら変えない(wikiのURLになる)
title: 企画コンセプト
spec_version: 0.1
updated: 2026-09-09
status: draft
---
```

### status のライフサイクル
| status | 意味 | 扱い |
|---|---|---|
| `draft` | 検討中。変わりうる | 実装の根拠にしてよいが、変更は自由 |
| `review` | 固めにかかっている | 変更時は D-nn に理由を残す |
| `fixed` | 確定。実装済みで動いている | 変更は**破壊的変更**として扱い、CHANGELOG に必ず記載 |
| `obsolete` | 廃止 | **削除しない**。冒頭に後継へのリンクを置いて残す |

### 暫定値のマーカー
未確定の数値には `【暫定】` を付ける。`status: fixed` にする際に**全て外れていること**を確認する。

---

## 6.5 ID規約 ― 追記のみ(append-only)

**wiki の permalink が壊れないための最重要規約。**

| 名前空間 | 形式 | 例 |
|---|---|---|
| 決定事項 | `D-nn` | `D-03` |
| 未決事項 | `Q-nn` | `Q-01` |
| マイルストーン | `M-n` | `M-2` |
| リスク | `R-nn` | `R-01` |
| コンテンツ実体 | JSON の `id`(kebab-case) | `cleaner-drone`, `plasma-cutter` |

### 規約
1. **番号・IDは再利用しない。** 廃止したものは削除せず `status: obsolete` にして残す。
2. **IDは改名しない。** 表示名(`title` / `name`)だけを変える。
3. 欠番は許容する(廃止の痕跡として意味がある)。

---

## 6.6 相互参照の記法 ★スポイラー/wiki 化の鍵

docs と data の中の相互参照は、**機械が解決できる形**で書く。
これがそのまま wiki のリンクに変換される。

| 記法 | 意味 | 変換先(wiki) |
|---|---|---|
| `[[mon:cleaner-drone]]` | 敵 | 敵ページ |
| `[[item:plasma-cutter]]` | アイテム | アイテムページ |
| `[[ego:sealed]]` | 改修品MOD | エゴページ |
| `[[uniq:the-warden]]` | 固有機材/ユニーク | 個別ページ |
| `[[lin:voidborn]]` | 系統 | 系統ページ |
| `[[role:netrunner]]` | ロール | ロールページ |
| `[[site:ark]]` | サイト | サイトページ |
| `[[term:seal]]` | 用語(glossary) | 用語ページ |
| `[[D-03]]` `[[Q-01]]` | 決定/未決 | 決定事項ページの該当節 |
| `[[doc:core#21]]` | 文書の節 | 該当文書 |

- **未解決の `[[...]]` は `check_docs.js` がエラーにする**(タイポと消えたIDを検出)。
- 通常の Markdown リンク `[表示](docs/xx.md)` は人間向け。相互参照は `[[...]]` を使う。

## 6.7 スポイラー / wiki 生成パイプライン

```
src/data/*.json ─┬─ tools/gen_reference.js ─→ docs/reference/*.md    開発者向け参照表
                 └─ tools/gen_spoiler.js   ─→ dist/spoiler/*.{json,md,html}

docs/*.md + docs/reference/*.md
                 └─ tools/gen_wiki.js      ─→ dist/wiki/             wiki取り込み用
```

### 生成物の規約
- 先頭に必ず**生成バナー**を入れる:
  `<!-- GENERATED by tools/gen_reference.js — DO NOT EDIT. 正本: src/data/monsters.json -->`
- `check_docs.js` は**再生成して差分が出たら落とす**(`build.py --check` と同じ思想)。
- `dist/` はコミットしない(生成物)。`docs/reference/` は**コミットする**
  (GitHub 上でレビューでき、変更が diff に出るため)。

### スポイラー段階(spoiler level)
一括で全部出すと未プレイの人が読めない。**3段階**で出し分ける。

| level | 内容 | 想定読者 |
|---|---|---|
| 1 基本 | 存在と分類のみ。店で買えるもの、系統/ロールの説明 | 初見プレイヤー |
| 2 標準 | 出現深度・耐性・おおよその強さ | 攻略を調べる人 |
| 3 完全 | 内部数値・出現確率・固有機材の全能力・《起源》の構造 | 開発者/やり込み |

`src/data/*.json` の各フィールドに `spoiler: 1|2|3` を付け、生成時に閾値でフィルタする。

### wiki 化の前提(今のうちに守っておくこと)
1. **すべての実体に安定IDがある**(§6.5)
2. **相互参照が機械可読**(§6.6)
3. **説明文が data 側にある**(`desc` フィールド)。docs には書かない
4. **1実体 = 1ページ**に分解できる粒度でデータを持つ

→ この4つさえ守れば、wiki 化は**後から生成器を書くだけ**で済む。今すぐ作る必要はない。

---

## 6.8 バージョニング

- `spec_version`: 企画書全体の版。**破壊的な設計変更**で minor を上げる(0.1 → 0.2)。
  M1〜M5 の各完了時にも上げる。文書ごとに個別の版は持たない(全文書で揃える)。
- `save_schema`: セーブデータの版。互換性のない変更で +1。`docs/01` で管理。
- `CHANGELOG.md`: **spec_version 単位**で区切り、その版で何を変えたかを列挙する。

## 6.9 検査(`node tools/check_docs.js`)

コミット前に必ず通す。以下を機械的に検査する。

| # | 検査 |
|---|---|
| C-1 | 全 `docs/*.md` に必須フロントマター(`doc` `title` `spec_version` `updated` `status`)がある |
| C-2 | `spec_version` が全文書で一致している |
| C-3 | `doc:` ID が重複していない |
| C-4 | `SPEC.md` の索引が `docs/*.md` を過不足なく列挙している |
| C-5 | Markdown の相対リンクが実在するファイルを指している |
| C-6 | `[[...]]` 相互参照がすべて解決する |
| C-7 | `D-nn` `Q-nn` に重複がない / 参照されているIDが実在する |
| C-8 | `status: fixed` の文書に `【暫定】` が残っていない |
| C-9 | 生成物(`docs/reference/**`)を再生成して差分が出ない |
| C-10 | `docs/*.md` に大きな数値表が手書きされていない(§6.1 違反の検出) |

> 生成器やデータがまだ無い段階では、該当検査は **skip** として報告し、失敗にはしない。
